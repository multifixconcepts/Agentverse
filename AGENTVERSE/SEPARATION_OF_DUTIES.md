# Separation of Duties — AgentVerse 2.0

**Version:** 2.1
**Status:** Active
**Gate:** Process Enforced

---

## Core Rule

> **No agent should approve its own work.**

This is the foundational principle of AgentVerse 2.0 enforcement. Every deliverable must be produced by one agent and verified by a different agent. No agent may both create and certify a piece of work.

---

## Roles

### IMPLEMENTER

**Can:**
- Edit source code, configuration, documentation
- Run tests locally
- Produce evidence files (test output, lint output, screenshots)

**Cannot:**
- Declare a gate PASS
- Self-certify their own work
- Modify verification scripts or gate verdict files

---

### VERIFIER

**Can:**
- Run tests against an implementation
- Inspect implementation artifacts
- Reject work with documented reasons
- Produce verification evidence
- Generate gate verdict JSON via verification scripts

**Cannot:**
- Modify the implementation under review
- Override a failing test result
- Skip verification steps

---

### RELEASE AUTHORITY

**Can:**
- Verify that all required gates have passed
- Verify artifact integrity (checksums, signatures)
- Verify deployment readiness
- Execute release and promote to production
- Confirm deployment succeeded post-release

**Cannot:**
- Modify implementation code
- Modify test code to change outcomes
- Bypass gate verification

## Gate Verdict Integrity

**Rule:** Gate verdict JSON is generated by verification scripts, not by agents.

Verification scripts (`_tools/verify-gate.sh`, `_tools/verify-*.php`) produce deterministic verdict files. No agent manually edits or creates verdict JSON. Agents may *request* verification, but they **cannot determine the result**.

```
Agent requests verification
        ↓
Verification script executes
        ↓
Script writes verdict JSON (PASS / FAIL / BLOCKED)
        ↓
Agents read verdict — cannot modify it
```

---

## Enforcement Rules

1. **An agent can REQUEST verification but cannot DETERMINE the result.**
2. **A gate PASS verdict must come from a verification script, not from any agent's assertion.**
3. **If an agent has a conflict of interest (authored the code AND is verifying it), the verification must be reassigned.**
4. **All role assignments and gate mappings are recorded in `AGENTVERSE/STATE_MAP.json` and enforced at runtime.**

---

## Conflict Resolution

If a role conflict is detected (e.g., the same agent wrote and is verifying code):

1. The CI pipeline flags the conflict.
2. The verification task is reassigned to a different agent of the same role type.
3. The conflict and its resolution are logged in the ticket's evidence chain.

## Verifier Unavailability Procedure

When the required verifier for a gate is unavailable, the following procedure applies. This is the ONLY path from IMPLEMENTED to any state other than VERIFIED or FAILED.

### Detection

1. Implementer attempts to route verification to the required gate owner.
2. If the gate owner agent is unavailable (no agent file, no contract, no response), the implementer records VERIFICATION_BLOCKED.

### Escalation

1. Implementer notifies the division council (or Summoner).
2. Division council searches for a qualified substitute verifier per the substitute selection rules.
3. If a qualified substitute is found, verification is assigned and proceeds normally.
4. If no qualified substitute is found, the ticket remains in VERIFICATION_BLOCKED.

### Release prohibition

Release authority MUST check all tickets in the release set. If ANY ticket has status VERIFICATION_BLOCKED, the release is BLOCKED. The release authority cannot:
- Skip the blocked ticket
- Override the blocked state
- Approve release with "verified by exception"
- Self-certify the blocked ticket's verification

### Resume procedure

When a qualified verifier becomes available:
1. The verifier reads the ticket, all generated evidence, and the blocked-state record.
2. The verifier independently performs verification per the gate's requirements.
3. The verifier transitions the work to VERIFIED or FAILED based on evidence.
4. The blocked-state record is preserved in the ticket's evidence chain as historical context.

### Failover during verification

If the verifier disappears during verification (model failover, session loss):
1. The work remains in its current state (not VERIFIED, not FAILED).
2. The new model must determine if verification was completed before the disappear event.
3. If verification was not completed, the work is treated as VERIFICATION_BLOCKED.
4. The new model must NOT self-approve the work.
